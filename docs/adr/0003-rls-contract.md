# ADR 0003: Row-Level Security contract and tenant secrets

- Status: proposed (Phase 0)
- Date: 2026-10-31
- Related: ADR 0001, ADR 0002

## Context

Smokey has one global `db` (`drizzle(new Pool(...))` in `src/db/index.ts`) imported by
every DAO. DAOs are static classes; some methods accept a `Tx`/`Executor` to compose into
a caller's transaction (checkout, receipts, sweeps). Ownership is enforced in each DAO's
`WHERE`. Background sweeps (`src/logic/orders/order-sweeps.ts`, every five minutes from
`src/instrumentation.ts`) and the payment reconcile job read across all orders.

The platform puts every shop in one database. A single missed `where tenant_id = …` must
not leak another shop's orders. So isolation is enforced twice: Postgres Row-Level
Security, and DAO scoping. Either alone is a bug waiting for one mistake.

## Decision

### 1. Database roles

| Role | Login | Owns tables | RLS | Used by |
| --- | --- | --- | --- | --- |
| `platform_owner` | yes | **yes** | `BYPASSRLS` (explicit; `FORCE` would otherwise filter the owner too) | migrations, backfills and data scripts only (`scripts/migrate.mjs`, `APP_CONFIG_DATABASE_MIGRATE_URL`) |
| `app_user` | yes | no | **enforced** (`NOBYPASSRLS`) | the app: every request, every sweep |
| `app_auth` | yes | no | n/a (no tenant tables granted) | Better Auth's adapter only: its own tables, a separate pool |
| `app_platform` | yes | no | `BYPASSRLS` | platform-admin DAOs only (`src/db/platform/`), Phase 4; a separate pool, `APP_CONFIG_DATABASE_PLATFORM_URL` |

- Every tenant table has `ENABLE ROW LEVEL SECURITY` **and** `FORCE ROW LEVEL SECURITY`.
  `FORCE` applies to the table owner as well, so `platform_owner` is given `BYPASSRLS`
  explicitly; without it every backfill, seed and the Phase 5 import running as owner
  would see zero rows and fail `NOT NULL` on insert. Seeds that act *as a tenant*
  (`seed-demo`, `seed-shipping`) run through `withTenant` on the `app_user` pool instead.
- Adding `tenant_id` to an existing table is always three steps in one migration:
  add nullable, backfill (dev/CI rows go to a default tenant), then `SET NOT NULL`.
- `app_user` gets `SELECT, INSERT, UPDATE, DELETE` on tenant tables, `USAGE, SELECT` on
  their sequences, `SELECT` on global reference tables (`provinces`, `tenants`,
  `tenant_domains`), and on Better Auth's tables only `SELECT (id, phone_number)` on
  `user` (for the customer list's phone column) and nothing on `session`/`account`/
  `verification`. Better Auth itself uses `app_auth`. `ALTER DEFAULT PRIVILEGES` covers
  future tables and sequences. No DDL, no `TRUNCATE`, not a member of `platform_owner`.
- Dev and CI create the roles in a Postgres init script; production creates them once by
  hand (documented in `docs/DEPLOY.md`). Migrations grant to `app_user` explicitly, and a
  test fails when a tenant table lacks the grants or the policy.

### 2. The policy

One policy per tenant table, the same text everywhere (generated by a migration helper so
it cannot drift):

```sql
alter table orders enable row level security;
alter table orders force row level security;
create policy tenant_isolation on orders
  using (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
  with check (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);
```

- `current_setting(…, true)` returns `NULL` when the setting was never defined on the
  connection. On a pooled connection that once ran `SET LOCAL`, it returns `''` after
  the transaction ends; `''::uuid` would **raise**, hence `nullif`. Either way the
  comparison is `NULL` and **no row matches**: no tenant means zero rows, not an error and
  not every row.
- `with check` makes an insert or update that names another tenant fail.
- `tenant_id uuid not null default nullif(current_setting('app.tenant_id', true), '')::uuid`
  so inserts are tenant-stamped without the DAO passing it; with no tenant set the insert
  fails on `NOT NULL`.

### 3. How a request gets its tenant

```ts
// src/db/tenant-context.ts (server-only)
const als = new AsyncLocalStorage<{ tenantId: string; tx?: Tx }>();

export function withTenant<T>(tenantId: string, fn: () => Promise<T>): Promise<T>;
export function withTenantTx<T>(fn: (tx: Tx) => Promise<T>): Promise<T>;
export function currentTenantId(): string;  // throws outside a tenant context
export function executor(): Executor;        // see below
```

- `resolveHost(host)` maps `Host` → `tenant_domains` → tenant (cached in-process,
  invalidated on domain change). Only the `Host` header is read, never
  `X-Forwarded-Host`; the reverse proxy (Traefik) overwrites `Host` with the requested
  host. Unknown hosts get 404. The tenant id is never read from a cookie, URL or body.
- **Two entry paths, because `AsyncLocalStorage` does not span a Next render.** Next's
  `proxy` runs in a separate invocation, and layouts and pages render as parallel RSC
  trees, so a layout cannot wrap the page in `als.run`.
  - **Server components, `generateMetadata`, `sitemap.ts`, `robots.ts`:** the tenant comes
    from Next's own request scope: `getRequestTenant = cache(async () =>
    resolveHost((await headers()).get('host')))`. `src/logic/` read functions called from
    RSC take no tenant argument; they call `await currentTenantId()`, which consults ALS
    first and falls back to `getRequestTenant()`. So `currentTenantId()` and `executor()`
    are **async**.
  - **Hono (`/api`), the Better Auth route handler, server actions, sweeps:** the entry
    point resolves the host and wraps the rest in `withTenant(tenant.id, …)` (`als.run`
    around `next()` for Hono).
  - **Caches:** anything memoised beyond one request (`src/lib/cache/store.ts`, and any
    future `'use cache'`/`unstable_cache`) receives the tenant id explicitly as part of its
    key; it never reads the request scope inside the cached function.
- **Per-operation transactions, not per-request.** Holding one connection for a whole
  server render (Next streams RSC for seconds) would exhaust the pool. So:
  - `executor()` inside `withTenantTx` returns that transaction.
  - Outside one, a DAO call runs as a short transaction:
    `BEGIN; select set_config('app.tenant_id', $1, true); <query>; COMMIT`.
    `set_config(…, true)` is `SET LOCAL`: it dies with the transaction, so a pooled
    connection never carries a tenant into the next checkout of that connection.
  - Multi-statement logic that must be atomic (checkout, receipts, transitions) opens
    `withTenantTx` explicitly, exactly where Smokey opens `db.transaction` today.
- **DAOs never take a `tenantId` parameter.** They call `executor()`. Where a query can
  name the tenant cheaply, the DAO also filters `tenant_id = currentTenantId()` (belt and
  braces: the integration tests run with RLS on, and the DAO filter makes a missing policy
  visible in review).
- **Global tables get their own executor.** `globalExecutor()` (the `app_user` pool, no
  tenant setting) is allowed only in an explicit list of global DAOs: `TenantDao`
  (`tenants`, `tenant_domains`, used by `resolveHost` and the sweeps' tenant list),
  `UserDao`, `OtpSendLogDao`, `HealthDao`, the provinces read. The list mirrors the
  catalogue test's global allowlist (§5), and an ESLint rule restricts the import to those
  files.
- `src/db/index.ts` stops exporting a pool-bound `db` to the app. ESLint
  `no-restricted-imports` allows the raw pools only in `src/db/tenant-context.ts`, the
  global DAOs above, `src/lib/auth/` (the `app_auth` pool), `src/db/platform/**`,
  `scripts/` and test setup.
- Outside any tenant context, `executor()` **throws** (fail closed in the app) and, if code
  somehow reaches the pool directly, RLS returns zero rows (fail closed in the database).

Overhead: a single-query DAO call becomes four round-trips on one connection
(`BEGIN`, `set_config`, query, `COMMIT`). Phase 1 measures it on the shop listing; if it
matters, batch reads of one render into one `withTenantTx`.

### 4. Background jobs

- Sweeps and reconcile list active tenants from `tenants` (global, readable by
  `app_user`), then run each tenant's sweep in its own `withTenant`. One tenant's failure
  is reported with its tenant tag and does not skip the others.
- No job uses `app_platform`. Cross-tenant reporting (platform dashboards) is Phase 4 and
  goes through `app_platform` DAOs under `requirePlatformAdmin`.

### 5. Global tables (explicit allowlist)

Tables without `tenant_id`, each with a reason, pinned by the catalogue test:

| Table | Why global | `app_user` access |
| --- | --- | --- |
| `tenants`, `tenant_domains` | resolved before a tenant exists | `SELECT` (+ writes via platform/signup logic) |
| `user`, `session`, `account`, `verification`, `rate_limit` | Better Auth identity (ADR 0002); `session.tenant_id` checked in app | none, except `SELECT (id, phone_number)` on `user`; Better Auth uses `app_auth` |
| `otp_send_log` | per-phone throttle across shops | `SELECT, INSERT, DELETE` |
| `provinces` | reference data | `SELECT` |

Everything else has `tenant_id` and the policy. A new table must either join the
allowlist in the test with a reason or get the policy.

### 6. Keys, sequences, foreign keys and caches

- Uniques become per tenant: `(tenant_id, slug)`, `(tenant_id, sku)`, `(tenant_id, code)`,
  `(tenant_id, province_id)`, `(tenant_id, key)` for content.
- **Cross-tenant FKs are impossible by construction:** child tables reference
  `(tenant_id, id)` of the parent (composite FK on a `unique (tenant_id, id)`), so an
  order item cannot point at another shop's product even with a forged id.
- `orders.order_no`: per-tenant counter (`tenant_counters` row, `unique (tenant_id,
  order_no)`), so numbers start at 1 per shop and reveal nothing about other shops. The
  counter row is locked **last** in checkout's lock order (customer row, then product rows
  by id, then the counter), so it cannot deadlock against Smokey's existing ordering.
- `payments.authority` stays globally unique. The Zarinpal callback arrives on the shop's
  host; tenant is resolved from the host first, then the payment is looked up by
  authority under RLS. A callback replayed on another shop's host finds nothing.
- Storage keys `t/<tenantId>/…`; the uploads route refuses a key whose prefix is not the
  request's tenant.
- In-process cache keys and tags, rate-limit buckets and the client cart's localStorage
  key all include the tenant id.

### 7. Tests that prove it (mandatory, Phase 1, run in CI against real Postgres as `app_user`)

1. **Zero rows:** for every tenant table, with no tenant set, `select count(*)` returns 0,
   an insert fails, and every DAO read method returns empty/null (the DAO-level version
   calls each DAO through the raw `app_user` pool, bypassing `executor()`'s throw).
2. **Catalogue:** query `pg_class` / `pg_policies` / `information_schema`: every table not
   in the global allowlist has a `tenant_id uuid not null` column, `relrowsecurity` and
   `relforcerowsecurity` true, the `tenant_isolation` policy with the exact expression, and
   the grants (tables and sequences). Also: `app_user` is not `BYPASSRLS` and owns
   nothing; `app_user` has no grant on `session`/`account`/`verification` and only
   `(id, phone_number)` on `user`. While Phase 1 migrates tables one story at a time, the
   test carries an exact `PENDING` list and asserts both ways: every pending table lacks
   the policy and every other table has it, so a stale entry fails the build.
3. **Cross-tenant:** seed tenants A and B with the same slugs/SKUs/phone; every DAO and
   every API route under tenant A never returns, updates or deletes B's rows, including
   with B's ids in URL/body (IDOR). Composite FKs refuse an A item on a B product.
4. **Pool hygiene:** on a pool of size 1 (so the same physical connection is reused),
   after a `withTenant(A)` call a query with no tenant sees zero rows (pins the
   `SET LOCAL` + `nullif` reasoning).
5. **E2E:** two hosts (`a.localhost`, `b.localhost`), a shopper orders on A, B's admin
   sees no trace of it; A's session cookie on B is signed out.

### 8. Tenant secrets, encrypted at rest

Secrets: Zarinpal merchant id, SMS provider API key, Umami credentials, later webhook
signing keys. Stored in `tenant_secrets (tenant_id, name, ciphertext, key_version,
updated_at, updated_by)` under RLS.

- **Algorithm:** AES-256-GCM (Node `crypto`), a fresh random 96-bit IV per write, 128-bit
  tag. Stored as `v<key_version>:<base64(iv | ciphertext | tag)>`.
- **Associated data:** `tenant_id + ':' + name + ':' + key_version`. A ciphertext copied to
  another tenant, another secret name or relabelled with another key version fails to
  decrypt instead of being accepted.
- **Keys:** a keyring in env, `APP_CONFIG_SECRETS_KEYRING` =
  `{"1":"<base64 32 bytes>", …}` plus `APP_CONFIG_SECRETS_KEY_CURRENT`. Never in the
  database or the repo. Rotation: add a version, set it current, a script re-encrypts all
  rows, then a verification pass decrypts every row with the
  new key, and only then is the old version removed. Missing keyring in production refuses to start
  (like Smokey's `assertReadyToServe`).
- **Access:** only `src/lib/secrets/` decrypts, server-only; decrypted values never enter
  logs, Sentry events (extend `sentry-privacy` tests), API responses or the client. The
  admin shows `••••1234` and accepts a replacement, never displays the stored value.
- **Payout destinations** (card-to-card number, Zarinpal merchant id) are where an
  attacker profits: changing one diverts a shop's money. The card number is not secret
  (every buyer sees it at checkout); it is stored in `tenant_settings` under the same GCM
  envelope, which only resists direct database tampering, since the app itself can
  re-encrypt anything. The real controls are in the app: changing either requires the
  **owner role and a fresh OTP** (step-up, not just a session), every change is written to
  `tenant_audit_log`, and the owner gets an SMS when it changes.
- **Tests:** round-trip; wrong tenant/name AAD fails; tampered ciphertext fails; rotation
  re-encrypts; a DB dump contains no plaintext secret (grep test on a seeded row).

## Consequences

- Every DAO changes mechanically (`db` → `executor()`), and every integration test runs
  inside a test tenant. That is most of Phase 1's diff, which is why it is split into
  stories that each leave CI green.
- Better Auth's tables stay outside RLS; their protection is ADR 0002's session binding and
  the rule that no tenant route reads `user` except through `customers`.
- `app_platform` exists but is unused until Phase 4, so Phase 1 has no BYPASSRLS path in
  the running app at all.
